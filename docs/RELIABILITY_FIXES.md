# 可靠性修复与下一轮交互优化

本轮修复真实评测暴露的结束协议与运行器问题，并针对补问前多余查询调整规划提示。没有新增业务权限，没有修改历史数据集、评分器、轨迹或实验结果。真实 API 调用为 0。

## 已实现

| 问题 | 修复 | 验证范围 |
|---|---|---|
| 正常规划步骤被记录为 retry | runtime 为每次逻辑模型调用绑定 `logical_call_id`，重试才递增 `attempt_index`；transport 单独记录 `http_index_in_turn` | Mock HTTP 运行真实 Agent：查询成功 → 下一步 503 → 重试成功，重试标记为 false / false / true |
| 查询后只输出文字，遗漏结束工具 | 最多进入一次协议纠正；丢弃自由文本，仅发送已有工具观察与固定纠正提示；只提供并强制选择 `finish_response` | 多轮“取消改查询”回归正常结束；同键重复请求不增加调用 |
| 纠正轮可能再次越界或编造证据 | runtime 在执行前拒绝纠正轮的非结束工具；结束工具仍执行原 schema、订单/退款查询与引用检查；纠正失败立即结束 | 提交、执行、跨用户读取及混合批次均不执行；没有查询证据时仍失败 |
| 补问意图/订单前多余读取订单列表 | Prompt 明确先补问；`list_my_orders` 描述限定为用户明确要求列出或协助选择订单 | 工程回归通过；尚无新的真实模型效果结论 |
| 克隆或文件缺失可能重置预算账本 | 默认只打开已有账本；仅首次准备可创建；有 release、export、started 标记时不得补建；空账本、缺失 terms/schema 均拒绝 | 离线恢复/缺失文件测试在 HTTP 前阻断 |
| 账本回退或替换 | 运行前与最近导出的 terms 和逐条历史 attempt 前缀核对 | 导出不一致即停止，未解析 usage 仍保留预留并阻断 |

纠正受原有最大步数、工具数、上下文、超时与运行关闭检查约束；不会扩充限额。一次纠正可能增加一个逻辑 LLM 调用，瞬时网络错误仍受已有重试上限约束。没有关闭 `UNVERIFIED_RESPONSE` 保护，也不会直接向客户输出模型自由文本。

指定结束工具使用 DeepSeek 官方 `tool_choice` 协议，保留现有 `thinking=disabled`。官方说明指定工具不支持思考模式；已按非思考模式检查请求契约，但本轮没有真实 API 联调。[DeepSeek Chat Completions 文档](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)

退款金额、政策判断、审批、收货确认和模拟执行继续由原确定性后端处理；Agent 工具没有审批或执行能力。前端和 API 契约未修改。

## 冻结实验与版本边界

- [原专项结果](RELIABILITY_HOLDOUT_EVALUATION.md) 保持 Dev 13/13、Holdout 25/26；本轮未重新运行 Holdout，未将失败改判成功。
- [原失败分析](RELIABILITY_FAILURE_ANALYSIS.md) 与原 `is_retry` 字段完整保留；新字段语义仅适用于本轮以后的调用。
- 原有 125 条评测数据、历史 50 条 Test，以及新增 26 条 Holdout 均未修改。已看过的失败进入工程回归，不能再当作未见样本。
- 历史模型实验的代码由各批次 `code_commit` 与 release hash 标识；可在 Git 历史中查看。旧运行器和旧 Prompt 对应的是历史版本，不应将历史成绩标成当前修复版本成绩。
- `scripts/reliability_live.py` 当前为修复版本；原 release/manifest 保持不动，`verify` 会因源代码变化拒绝继续旧实验。这是冻结保护的正常行为，不应重写旧 hash 消除此检查。
- 后续真实评测需要新实验目录、新版本清单和未消费的 Holdout，先确认新的 API 预算。本轮没有创建或启动新模型实验。

## 预算恢复边界

`budget.db` 是本地持久账本，被 Git 忽略；Git 中的 `budget-export.json` 是审计记录，不能自动证明最后一次 HTTP 请求未发生。

跨电脑或克隆仓库时，应保留原目录与 SQLite 账本备份，停用写入进程后核对备份和导出。账本缺失、导出不匹配或 usage 不明时停止调用；本轮没有实现从 JSON 自动重建账本，也不会自动清除开始标记、回放请求或解冻 Holdout。

## 下一轮：前端交互流畅度

保留已有视觉设计，先优化客户售后主路径，再优化管理员工作台。以下为待实施计划，尚未完成。

1. **先记录基线。** 用本地脚本模型测量页面导航、发送反馈、长对话滚动、列表刷新和大 Trace 展开；固定浏览器、视口、数据与网络条件。组件测试、浏览器 E2E 与真实模型延迟分开报告。
2. **对话即时反馈。** 发送时立即展示用户消息与真实等待状态，保留输入和恢复信息；自动滚动仅在接近底部时触发，用户查看历史时不抢滚动；提供新消息提示、键盘操作与 reduced-motion 支持。不伪造业务处理进度，不以逐字显示未验证模型文字冒充安全流式回复。
3. **数据请求与刷新。** 当前 `useData` 已忽略过期结果，但未取消请求；增加 GET 请求取消、重复读取合并及范围明确的刷新。已完成数据刷新时保留内容，显示更新反馈；缓存按账号/权限/资源隔离，登出清理，审批或申请成功后失效相关状态。
4. **等待与失败恢复。** 已知 run_id 仅查询原运行；未知结果保留原请求与幂等键。控制轮询节奏，页面离开停止无用 GET；切回页面核对服务端状态。停止浏览器等待不代表取消后端业务，不自动生成新提交。
5. **管理员与长列表。** 列表分页、筛选状态与详情按需加载；大 Trace 按调用折叠，展开时再渲染详细 JSON。审批/确认收货/模拟执行反馈来自服务端，禁止乐观宣告成功。
6. **验收。** 验证导航、重复点击、慢响应、网络断开、刷新恢复、会话过期和账号切换；补充组件与浏览器回归，保留前后测量。若发现后端响应才是主要瓶颈，单独分析，不用前端动效代替性能证据。

下一轮优先采用现有框架和接口，不默认引入新的状态管理库、复杂缓存架构或后端异步任务系统。RAG 仍待政策语料与检索需求证据后决定。
