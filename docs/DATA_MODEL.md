# 数据模型

Stage 3 当前合计 **14 张表**。下面先描述原有 11 张，再说明新增的 3 张；原表结构和数据保持兼容。

## 表与关系

| 表 | 关键内容 | 关系/约束 |
|---|---|---|
| users | 姓名、唯一邮箱、创建时间 | 一个用户多个 orders/tickets |
| orders | 用户、状态、币种、原价/优惠/实付、支付/发货/签收时间 | CNY；订单状态与时间 CHECK；用户外键 |
| order_items | SKU、名称、分类、数量、单价、优惠分摊、实付、退货标记、实收退货数量 | 所属订单；正数量；退货数量不超购买量 |
| shipments | 模拟承运商、唯一单号、状态、时间、最新事件 | order_id 唯一，V1 单订单单包裹 |
| refunds | 订单/商品、数量、金额、原因、状态、唯一幂等键 | 可选 action_request_id 唯一；商品必须属于订单 |
| tickets | 用户、可选订单、问题类型、描述、状态、优先级 | 订单/用户组合外键防止跨用户关联 |
| approvals | 所属工单/申请、动作、金额、结果、审核人、理由、时间 | 每个申请最多一条；非待审必须有审核信息 |
| action_requests | 原始建议、政策授权、政策决策、执行状态、金额、数量、证据标记、版本与快照 | 用户/幂等键唯一；订单/商品/工单归属组合约束 |
| audit_events | 申请、事件类型、操作者、JSON 数据、时间 | 每申请多事件，只读 API |
| agent_runs | 用户/订单/工单、查询、建议/最终动作、风险、已知 token 汇总/延迟/错误等 | Stage 3 每次对话创建运行；完整用量见 model_calls |
| tool_calls | 运行、工具名、参数/结果、状态、延迟/错误 | Stage 3 多个工具调用属于一次 AgentRun |

上表为 Stage 1–2 的 **11 张表**：原计划 9 张，加上 `action_requests` 和 `audit_events` 2 张。Stage 3 开始实际使用 agent_runs/tool_calls，新增以下表：

| 表 | 用途 |
|---|---|
| ticket_submissions | 用户 + 幂等键唯一、请求指纹与工单映射，避免重复创建工单 |
| agent_run_details | 与 AgentRun 一对一；会话父轮、幂等键、模型、回复、结果类型、来源快照、关联业务申请和结束时间 |
| model_calls | 每轮各次模型调用与重试；请求/响应、is_live、可空 token、延迟和错误 |

新增表由 init-db 的 create_all 非破坏性补建，本次不修改旧表，暂不需要批量重建 SQLite 表。旧 agent_runs 整型 token 汇总只计已知值，对外权威用量从可空的 model_calls 计算，未知返回 null。

> 若查看 SQLite 实际 schema，以 `Base.metadata` 和导出的 OpenAPI 为准；所有枚举统一在 `core/enums.py` 中。

## 金额语义

所有金额列使用 `Money` 类型，SQLite 原始值单位是“分”，ORM 属性是 Decimal。API 为固定两位小数字符串。数据库 CHECK 表达式以原始整数分计算，不混入浮点常量。

- `orders.original_amount` = Σ（商品单价 × 数量）。
- `orders.discount_amount` = Σ 商品项优惠分摊。
- `orders.payable_amount` 是计算属性：原价 − 优惠，不重复落库。
- `orders.paid_amount` 是历史实际支付金额；未支付为 0；已支付在本版本为一次全额支付。
- 退款不会减写 `paid_amount`，它保持原始支付事实；可退余额通过 refunds 计算。
- `order_items.paid_amount` 表示该商品行整体实付，不是每件均价。
- ActionRequest/Approval 的 amount 对退款表示拟退款金额；对换货表示用于风险判断的商品价值，不是资金流出。

优惠使用最大余数法按商品行原价比例分配；余数相同时按输入行顺序分配，seed 输入按固定商品顺序。商品数量均价可能有不足一分的尾差，前序部分退款取整分，最后一批补齐剩余额度。

例：一行 3 件实付 100.00 元，逐件退款为 33.33、33.33、33.34。存在换货时已换货数量不再退款，相关尾差可能保留，避免向剩余退款数量多分配价值。

## 状态与空值

- 没有退款用空列表 `[]` 表达，不在退款表创建 `NONE` 记录。
- 工单允许缺订单，以覆盖信息不足；只允许从缺失变为关联，不能换成另一订单。
- 整单取消退款的 `order_item_id/quantity` 都为空；商品退款二者都非空且数量为正。
- 未发货订单物流接口返回 HTTP 200 + `null`；订单不存在为 404。
- `proposed_action` 永久记录调用者建议；`authorized_action` 记录政策授权；`final_action` 仅成功后设置。
- 历史 seed 退款的 `action_request_id` 可以为空，表示模拟导入的既有售后记录，不伪造申请审计。
- `returned_quantity` 是模拟仓库已收到的退货数量；少件退款、换货不增加该数值。退款在途/失败仍可有已退货数量。

## 约束覆盖边界

数据库负责非负金额、合法枚举、外键、唯一性、行内数量/时间约束。服务负责跨记录余额、合法状态转移、跨订单归属和业务事务。`validate_seed` 负责检查订单与商品合计、签收物流以及退款总额的一致性。

当前没有公开订单/商品编辑 API。未来新增订单导入或管理写 API 时，必须复用或扩展跨表校验，不能假设单行 CHECK 会保证所有合计正确。原始 SQL 可以绕过服务的余额约束，这是数据库直连管理者的权限边界。

## 索引

用户订单、订单商品、退款的订单与状态、工单状态与创建时间、申请所属工单/用户/订单、审计所属申请等建立查询索引；邮箱、物流单号、幂等键、单申请退款和审批通过唯一索引约束。
